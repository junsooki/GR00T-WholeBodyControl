# Terminal 2 for H2 — status and porting guide

Terminal 2 is `gear_sonic_deploy`: the C++ program that runs the trained SONIC
policy (ONNX/TensorRT) and exchanges DDS messages with the robot or the MuJoCo
sim. Upstream ships it G1-only (29 motors). This doc tracks what we have for
H2 and what the full C++ port needs.

## What works today (no checkpoint, no GPU needed)

`tools/h2_dummy_controller.py` is a Python stand-in for Terminal 2. It speaks
the identical wire protocol (`rt/lowstate` in, `rt/lowcmd` out, unitree_hg
messages, 50 Hz, H2 gains from the sim yaml) but sends scripted targets
instead of policy actions.

```bash
# Terminal 1
python gear_sonic/scripts/run_sim_loop.py --wbc-version sonic_h2
# Terminal 2 (stand-in)
python tools/h2_dummy_controller.py \
    --config GR00T-WholeBodyControl/gear_sonic/utils/mujoco_sim/wbc_configs/h2_31dof_sonic.yaml \
    --mode wave
```

`wave` mode ramps to the default pose then swings head yaw, shoulder pitches,
and elbows — if the sim robot waves, the whole DDS/ordering/gain pipeline is
correct. `tools/test_h2_loopback.py` automates this headlessly (launches the
sim as a subprocess, asserts the head-yaw joint tracks the commanded sinusoid;
verified passing: correlation 0.98, RMSE 0.1 rad).

The dummy controller needs `unitree_sdk2py` — install the repo's vendored copy:
`pip install -e GR00T-WholeBodyControl/external_dependencies/unitree_sdk2_python`
(requires the CycloneDDS C library; on odd container glibc, pass
`--interface default` — explicitly naming `lo` can crash cyclonedds there).

## Ready-made ingredient for the C++ port

`deploy/h2_policy_parameters.hpp` (generated by
`tools/generate_h2_policy_parameters.py`, compiles standalone) is the H2 analog
of `src/g1/g1_deploy_onnx_ref/include/policy_parameters.hpp`, containing:

- `H2_NUM_MOTOR = 31`, upper body = 19, lower = 12
- IsaacLab↔MuJoCo DOF mappings (verbatim from training's `robots/h2.py`,
  verified as mutual inverses)
- upper/lower/wrist joint index lists in both orderings (derived, not typed)
- `h2_vr_3point_index` / `h2_vr_5point_index` (IsaacLab body indices:
  wrists 30/31, torso 9, pelvis 0, ankles 20/21)
- PD gains and default pose — verified numerically identical to the sim yaml,
  so training / sim / deploy agree by construction
- action scales `0.25 × training_effort / stiffness` per `robots/h2.py`

## The C++ port checklist (when the checkpoint is close)

All paths under `gear_sonic_deploy/src/g1/g1_deploy_onnx_ref/`:

1. **`include/robot_parameters.hpp`** — `G1_NUM_MOTOR = 29` and the
   `G1JointIndex` enum (G1 hardware order: ankle pitch-before-roll, no head).
   H2 needs its own 31-entry versions; note H2's real-robot SDK motor
   numbering must be confirmed against Unitree's H2 docs before hardware use —
   in sim it equals MJCF order.
2. **`include/policy_parameters.hpp`** — replace with
   `deploy/h2_policy_parameters.hpp` (done, above).
3. **`src/g1_deploy_onnx_ref.cpp`** (4.5k lines) — ~21 uses of `G1_NUM_MOTOR`,
   7 uses of the mapping arrays, obs assembly sized for
   `dof=29 / ref_upper=17`; H2 is `31 / 19`. Also strips: Dex3 hands
   (`dex3_hands.hpp`, H2 has none yet) and the G1 ankle series/parallel
   `Mode::PR/AB` handling if H2's ankles differ.
4. **`include/fk.hpp` / `src/fk.cpp`** — FK loads a MuJoCo XML; point it at
   `h2.xml` and audit `ReserveCapacity(..., joints = 29, ...)` defaults.
5. **`include/motion_data_reader.hpp`** — reference motions are 29-DOF G1
   retargets; H2 mimic/teleop needs H2-retargeted motion data (out of scope
   until motion retargeting is done).
6. **Observation config yaml** (`policy/release/observation_config*.yaml`) —
   write the H2 version to match however the H2 checkpoint is exported
   (encoder obs names/dims come from the training export, so this waits for
   the actual export).
7. **`deploy.sh`** — parameterize the hardcoded `g1_deploy_onnx_ref` target
   and policy paths.

Sizing: items 1–4 are mechanical once a checkpoint's obs layout is known
(a few days); 5 depends on retargeting; 6 falls out of the ONNX export.

## Contract with the training team

The exported H2 ONNX must use: MuJoCo-order actions (31), the
`h2_isaaclab_to_mujoco` mapping if exported in IsaacLab order, action scale
`0.25·effort/stiffness` from `robots/h2.py`, and the PD gains in this repo's
yaml. If any of those change in the training fork, regenerate
`h2_31dof_sonic.yaml` and `h2_policy_parameters.hpp` from the updated sources
(both are generator-produced).
